# Codex operating profile

This profile records the user's adoption preferences for these six engineering skills. Apply it before the upstream workflow. Explicit user instructions and applicable repository rules determine scope, commands and authorization; upstream examples are illustrative.

- Use only skills relevant to the current task. Keep rules files short and load supporting references on demand. Do not preload a pack-wide router or every skill.
- Continue autonomously inside the authorized scope. Reuse established decisions and existing authorization. Ask only for missing information that materially changes the outcome, an unresolved conflict that cannot be resolved from evidence, or a genuinely required authorization. An interview, a routine checkpoint, or an upstream example does not create a new approval requirement. Existing repository boundaries still apply.
- Prefer Codebase Memory graph tools for structural discovery when available. Confirm the nearest project and generation; default to Verify. After locating candidate files, check their index coverage. Read source for stale, partial, skipped, excluded or unknown coverage; disclose limitations. Use text search for literals and non-code files or insufficient graph evidence.
- Match process depth to impact: a clear small change needs a focused edit and relevant verification; a bug needs reproduction, root-cause analysis and regression protection; significant work needs explicit outcomes and small, verifiable capability slices. Reuse the project's spec, plan and tracker conventions; preserve unfinished work belonging to other tasks.
- Repository commands and conventions take precedence over generic examples. Inspect actual scripts before promising lint, build or tests. Do not introduce npm, unscoped builds or generic React patterns into a project that specifies pnpm, scoped checks or React Compiler constraints.
- Tests must prove observable behavior or meaningful invariants. Use focused tests during iteration and required repository checks at completion. Do not add tests for reversible, low-impact documentation/static edits or assertions that merely mirror implementation. Preserve meaningful assertions; do not skip tests, suppress checks or lower thresholds to make a change pass. Record pre-existing failures separately.
- Treat quality targets as measured, project-specific contracts. Reuse current checks; establish a baseline before introducing numerical budgets. Performance work compares the same scenario before and after a targeted fix. Avoid duplicate check runs and new tooling without a concrete need.
- A skill is guidance, not evidence of correctness or CI enforcement. Close work with the actual commands and outcomes, runtime evidence when applicable, and remaining limitations. Never claim a check ran or passed without evidence.
- Preserve decisions, pending tasks, changed files and verification outcomes in existing durable project artifacts when work spans sessions. Do not commit, merge, deploy, contact other people, or launch other agents merely because an upstream workflow suggests it; follow the user authorization and repository workflow applicable to that action.
